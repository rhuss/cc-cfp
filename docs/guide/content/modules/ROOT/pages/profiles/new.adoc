`cfp` ships with a profile for KubeCon + CloudNativeCon.
When your next talk goes to another conference, you build its profile with `/cfp:profile new`.
You point cfp at the conference's call for proposals, and it reads the public pages and any screenshots of the form you give it.
Then it drafts a profile and walks you through it, one section at a time.
Nothing lands in your store until you've approved every section.

This page shows you how a research run goes and what to watch for, so that the profile you end up with is one `/cfp:draft` can work with.
The terms profile, event, verification label, and relevance field are explained in xref:profiles/index.adoc[How profiles work].
If you'd like to see a finished profile first, xref:profiles/kubecon.adoc[The shipped KubeCon profile] has one with every part filled in.

The examples on this page use ExampleConf, a fictional conference.

== What cfp fetches and what it doesn't

`cfp` uses the web for this research, within fixed limits.
Its only network access during research is public CFP pages, reviewer guideline pages, and links you give it.
From the CFP page it follows links only to pages on the same host, or on a host you named.
For any other host it asks you first.

The submission form itself is a different story.
When a submission link redirects to a login, cfp never fetches it further.
That covers Sessionize `submit` links, pretalx `submit` links, and any sign-in page.
Instead, cfp stops, tells you the form is login-walled, and asks you for screenshots.

That's why screenshots matter so much.
The form usually sits behind a login, so screenshots of the live form are the most reliable source a profile can have.
You can pass them as files or paste them into the conversation.
For a pasted image without a file name, cfp asks you for a label such as `pasted-1`.
When a screenshot and a page disagree, the screenshot wins, and the profile's Notes section records the conflict.

Everything cfp fetches is data to it.
It takes facts from a page and never acts on instructions it finds there.

== The command and its arguments

`/cfp:profile new` takes the conference and two optional flags:

[source,text]
----
/cfp:profile new <conference name or CFP URL> [--event <id or URL>] [--screenshots <path,...>]
----

`<conference name or CFP URL>`:: The conference to research.
With a URL, cfp uses that page as the CFP page.
With a name, cfp searches the web for the CFP page and asks you to confirm it.
`--event <id or URL>`:: The edition you're researching.
`--screenshots <path,...>`:: A comma-separated list of screenshot files of the submission form.

Besides the profile for the whole conference family, cfp builds an event for one edition when your input names one.
A year in the name or the URL counts, and so does `--event`.
The event gets the edition's dates, tracks, location, and session type variations, and the profile never holds them.

== Research a conference

A profile tells `/cfp:draft` which fields to draft, how long each may be, which options exist, and which rules disqualify a proposal.
Here's what a run looks like, with ExampleConf as the conference.

. If you can open the submission form, take a screenshot of each page of it and save them, for example as `~/Desktop/exampleconf-form-1.png` and `~/Desktop/exampleconf-form-2.png`.
Skip this step when you can't get at the form yet.
You can add screenshots later with `/cfp:profile refresh`, which takes `--screenshots` too.

. In Claude Code, start the research with the CFP page and your screenshots:
+
[source,text]
----
/cfp:profile new https://exampleconf.example/2027/cfp/ --screenshots ~/Desktop/exampleconf-form-1.png,~/Desktop/exampleconf-form-2.png
----
+
Use your conference's real CFP page.
The URL here has a year in it, so cfp also builds an event for that edition.
+
When you give a name instead of a URL, cfp searches for the CFP page first.
It shows you the page it picked, up to two alternatives, and an "Other" option where you paste a URL.

. Let cfp read the sources.
It fetches the CFP page and the pages it links for rules, sample submissions, co-located events, and reviewer or scoring guidelines.
When the CFP page links no reviewer guidelines, cfp searches for them.
From each screenshot it reads the field labels and their order, the required markers, the option lists, the character counters, and hints about which fields only reviewers see.
Before it starts, cfp reads a research checklist that ships with the plugin, and it follows that checklist.

. Confirm the ids.
`cfp` derives a profile id from the conference family name, a short lowercase slug, and an event id from the profile id plus the edition.
For ExampleConf that would be `exampleconf` and `exampleconf-2027`.
It asks you to confirm both before it presents the sections.

. Go through the draft, one section at a time.
`cfp` shows each item with its value and its verification label, for example `abstract: longtext, required, limit 1300 [unverified]`.
The sections come in this order:
+
.. Session types: id, name, duration, minimum and maximum speakers, and notes.
.. Fields and limits: kind, required flag, limit, options, and audience for each field.
.. Tracks and dates, for the event: tracks, event dates, CFP open and close with the timezone, notification date, location, and submission limit.
`cfp` skips this section when there's no event.
.. Rules and rubric: each rule with its kind, severity, text, and source, then the rubric's scale, pass thresholds, and criteria.
.. Rejection reasons and the speaker bio: whether the form asks for a bio with each submission (`bio_on_form`) and, when it does, the bio limit.
+
After each section cfp asks one question: approve, edit, or re-research?
On edit, it asks what to change, applies it, and shows the section again.
On re-research, it goes back to the sources for that section only, fetching again or asking you for a screenshot, and then shows the section again.
+
The profile also gets a drafting guidance section.
`cfp` fills it with what reviewers reward and punish, any historic limits with the URL they came from, and its pass assumption when the conference published no pass threshold.
`/cfp:draft` reads that text later.

. Let cfp write the profile.
Once you've approved every section, cfp writes the profile, then the event, into your store as `profiles/<id>/profile.md` and `profiles/<id>/events/<event-id>.md`.
It validates both and fixes the data until the validation passes.
Then it approves the profile and the event, and it prints both file paths and the profile as `/cfp:profile show` renders it.

The validation checks the structure of the data.
It reports, among other things, a field or rule without an id, an id used twice, an unknown field kind, rule kind, severity, or label, and a limit that isn't a positive whole number.
For the event it also reports an empty track list (the track checks can't run without one) and a date that isn't an ISO date.
When something's wrong, cfp shows you the problems before it fixes them.

[NOTE]
====
The two files take their approval differently when cfp writes them again.
A profile that already exists keeps its `approved` flag when the data cfp writes has no such key, and the profile data cfp drafts has none.
An event always takes the flag from the data cfp writes, which is off unless set.
In the `new` flow cfp sets it for the event only because you approved every section.
====

== When nothing is public

Some conferences publish almost nothing.
There's no CFP page, or the page is a single paragraph, or the form is login-walled with nothing else public.
`cfp` says so plainly in that case.

Then it builds a small profile from what you tell it, asking one question at a time.
It asks for the platform, the session types with durations and speaker counts, the fields you remember with their limits, and the deadline.
Every limit is marked `unverified`, and every rule has an empty source.
`cfp` lists which items screenshots of each form page would verify, and it suggests that you run the command again with `--screenshots`.
You still approve every section before anything is written.

== What to record so that drafting works

Some parts of a profile need more care than others, because `/cfp:draft` and the pre-flight rely on them.
Keep the following in mind while you go through the sections.

=== Custom rules that can be checked

`cfp` has rule kinds for submission limits, repeat talks, tracks, speaker counts, all-men panels, panel companies, and vendor pitches.
A rule that fits none of them gets the kind `custom`.
The pre-flight check judges every custom rule against your proposal from its text, and it records a violation with the rule's severity.
So write the text as a rule a reader can check.

Here's the difference for a fictional ExampleConf rule.
"Workshops should be well prepared" gives the pre-flight nothing to check.
"A workshop abstract names the software attendees install before the session" does.

The severity is `disqualify` when the conference says it removes or doesn't select a proposal that breaks the rule, and `warn` otherwise.
xref:user/preflight.adoc[Pre-flight, counts, and the paste view] shows how the verdicts on custom rules come out.

=== A rule for one session type

When a rule covers only one session type, the rule gets `params.session_type` with that type's id.
The pre-flight then applies it only to proposals of that session type.
The ExampleConf rule above would look like this in the profile data:

[source,json]
----
{"id": "workshop-install-list", "kind": "custom", "severity": "warn",
 "params": {"session_type": "workshop"},
 "source": "https://exampleconf.example/2027/cfp/",
 "text": "A workshop abstract names the software attendees install before the session."}
----

=== Whether the form asks for a bio

The speaker bio isn't a form field in a profile.
It has its own keys, `bio_on_form`, `bio_limit`, and `bio_limit_status`, and it never goes into the field list.
Set `bio_on_form` to `false` only when your screenshots cover the complete form and show no bio.
Then `/cfp:draft` attaches no bio, and the paste view prints none.
When in doubt, leave it `true`.

=== Field ids

`cfp` uses snake_case field ids, so that the draft flow recognizes the same field across conferences.
When a field on your form matches one of these, use its id:

[cols="1,3"]
|===
|Id |Field

|`title` |The session title.
|`abstract` |The public session description or abstract.
|`value_to_community` |The reviewer-only relevance field (`benefits` on older forms).
|`audience_level` |The level of expertise of the intended audience.
|`track` |The track or topic selection.
|`format` |The session format or type selection.
|`case_study` |Yes or no: is this an end-user case study.
|`previously_presented` |Yes or no, or text, about earlier outings of the talk.
|`cncf_oss_projects` |The CNCF projects featured plus the other open source projects discussed, with links.
|`resources` |Additional resources such as earlier recordings, with kind `resources` for a list of links or `longtext` for one free-text box.
|===

A field that matches none of them gets a descriptive snake_case id of its own, such as `learning_outcomes`.
Give every reviewer-only text field other than the relevance field a guidance text that says what the form expects, because the draft flow writes it from that text.
xref:profiles/index.adoc[How profiles work] explains how cfp picks the relevance field.

== Check the new profile

Before you draft against the new profile, take one look at it together with its event.
This is the form your proposals are drafted against.

. In Claude Code, type:
+
[source,text]
----
/cfp:profile show exampleconf --event exampleconf-2027
----
+
Check: the header shows the profile's name, platform, and approval, then the event's name, location, dates, CFP open and close, notification date, days to close, and approval.
Both approvals are on.
The fields table lists each field's `limit_status`, and below it cfp names the relevance field or says the form has none.
Near the end, the bio line says "no bio on the form" when `bio_on_form` is false, and otherwise shows the bio limit with its label.

If the conference isn't shaped like KubeCon + CloudNativeCon, xref:profiles/second-conference.adoc[A second conference: what changes] covers what changes.
