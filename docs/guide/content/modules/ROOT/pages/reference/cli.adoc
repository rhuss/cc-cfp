`cfp/scripts/cfp_store.py` is the single CLI entry point for the cfp store.
cfp's skills run every deterministic operation through it and never edit store files directly.
You can also run it yourself from a clone of cc-cfp.
xref:internals/architecture.adoc[Architecture] explains why the skills go through the CLI.
This page lists every group, subcommand, and option, and the top-level keys each call returns.

== Invocation

[source,bash]
----
python3 -I cfp/scripts/cfp_store.py <group> <subcommand> [options]
----

A skill runs the same script as `python3 -I "$PLUGIN_ROOT/scripts/cfp_store.py"`.
`count` and `pasteview` have no group and take `--proposal` directly.
`preflight` runs with `--proposal` directly and has one subcommand, `add-finding`.
`--help`, after the script name or after a group, prints argparse help text instead of JSON.

The skills write long texts and free text to a file and pass the path with `--text-file` or `--from-json`.
Only ids, dates, numbers, and values from a fixed option list go into flags.

== Global options

[cols="1,3"]
|===
|Option |Effect

|`--store <path>`
|The store to work on.
Without it, the CLI takes the `CFP_STORE` environment variable, then the `store` value in `config.json` in the config folder, then the default `<data folder>/store`.
xref:reference/config.adoc#store-resolution[Configuration] describes the folders and their environment variables.

|`--today <date>`
|An ISO date (`YYYY-MM-DD`) used instead of the current date.
In a subcommand that reads it, a value that is not an ISO date is a usage error.
|===

Both options are accepted before the group, after the group, and after the subcommand.

Every subcommand except `config show` and `config init` needs an initialized store, that is, a store with a `config.md`.
On any other store the call fails with `store not initialized`.

These subcommands read `--today`: `profile list`, `profile show` (with `--event`), `event list`, `example add`, `bio write`, `talk write`, every `proposal` subcommand except `list` and `show`, `review record`, `preflight`, `preflight add-finding`, and `status set`.
The other subcommands accept it and do not use it.

== Output and exit codes

Every subcommand call prints exactly one JSON object on stdout.
On success it is `"ok": true` followed by the keys the tables below list.
The one exception is `pasteview --format markdown`, which prints markdown.

[cols="1,3"]
|===
|Exit code |Meaning

|0
|Success: `"ok": true`.

|1
|Domain error: `"ok": false` and an `error` text.
An unexpected failure also exits with 1, with an `error` text that starts with `internal error`.

|2
|Usage error: `"ok": false` and an `error` text that starts with `usage error`.
Unknown options, a missing subcommand, a missing required option, a bad `--today`, and malformed JSON in a flag are usage errors.
|===

The `list` subcommands and `preflight` also return `problems`, a list of `{path, error}` entries for store files with broken front matter.
xref:internals/store.adoc[Store files] describes those files.

Check: `config show` on a directory that is not a store reports it as missing and still succeeds.

[source,bash]
----
python3 -I cfp/scripts/cfp_store.py config show --store /tmp/cfp-no-store; echo "exit=$?"
----
// expect: matches /"exists": false/ and contains "exit=0"

Check: any other subcommand on that directory is a domain error.

[source,bash]
----
python3 -I cfp/scripts/cfp_store.py profile list --store /tmp/cfp-no-store; echo "exit=$?"
----
// expect: contains "store not initialized" and contains "exit=1"

[#config]
== config

Store configuration.

[cols="1,2,2"]
|===
|Subcommand |Options |Returns

|`show`
|None.
|`store`, `store_source` (`argument`, `environment`, `config`, or `default`), `exists` (whether `config.md` exists), `config` (the stored values, or the defaults when there is no `config.md`), `config_file` (the config file read, or `null`), `config_write_path` (the config file the next setup writes), `data_dir`, `user_profiles_dir`.
Fails on an invalid `CFP_DATA_DIR` or `CFP_CONFIG_DIR`.

|`init`
a|* `--speaker-name <name>`, required
* `--speaker-company <name>`
* `--voice-profile <name>`
* `--review-rounds <n>`, an integer
* `--default-profile <id>`
* `--seed-dir <path>`
* `--user-seed-dir <path>`: overrides the personal profiles folder (for tests)
|`store`, `created` (paths created), `seeded_profiles`, `config_write_path`, `user_profiles_dir`, `warnings`.
Without `--store`, the store is the one cfp resolves, by default `<data folder>/store`.
Creates the store folder with missing parents, its subfolders and `config.md`, and copies every seed profile from `--seed-dir` and from the personal profiles folder that the store does not have yet and marks it approved.
Without a default profile, it takes the first profile id in sort order.
It also writes the store path to `config.json` in the config folder, named in `config_write_path`.
`warnings` lists personal profiles that replace shipped ones and, when `CFP_STORE` names another store, that the variable overrides the saved store in later sessions.
Fails on an invalid `CFP_DATA_DIR` or `CFP_CONFIG_DIR` before it writes anything.

|`set`
a|* `--key <key>`, required
* `--value <value>`, required
|`key`, `value`.
`review_rounds` must be an integer.
|===

[#profile]
== profile

Conference profiles.
xref:internals/store.adoc[Store files] shows the profile and event files.

[cols="1,2,2"]
|===
|Subcommand |Options |Returns

|`list`
|None.
|`profiles` (id, name, platform, approved, seed version, and events of each), `problems`.

|`show`
a|* `--profile <id>`, required
* `--event <id>`
|The effective profile: `profile`, `event`, `session_types`, `fields`, `relevance_field`, `rubric`, `rules`, `rejection_reasons`, `submission_limit`, `bio_on_form`, `bio_limit`, `bio_limit_status`, `tracks`, `approved`, `drafting_guidance`, `notes`.
With `--event`, the event's overrides are merged in and `event` holds `days_to_close`.

|`validate`
a|* `--profile <id>`, required
* `--event <id>`
|`valid`, `problems`.

|`write`
a|* `--profile <id>`, required
* `--from-json <file>`, required
|`path`.
The JSON keys go into the profile's front matter, except `body`, `drafting_guidance`, and `notes`, which become body sections.
An existing profile keeps its approval unless the JSON sets `approved`.

|`approve`
a|* `--profile <id>`, required
* `--event <id>`: approve the event override instead
* `--revoke`: set approval to false
|`path`, `approved`.

|`seed-status`
a|* `--seed-dir <path>`, required: the shipped profiles
* `--user-seed-dir <path>`: overrides the personal profiles folder (for tests)
|`seeds`: one entry per seed profile, shipped or personal, with `profile`, `state`, `store_version`, `seed_version`, `files`, `source` (`plugin` or `user`), and `seed_dir` (the folder it was read from).
States: `missing`, `current`, `outdated`, `newer`, `local`, `unreadable`.
For an `outdated` profile, `files` lists each seed file as `same`, `changed` (with a `diff`), or `missing`.
The diff of a personal profile labels its side `user/<file>`, the diff of a shipped one `shipped/<file>`.
`warnings`: one entry per personal profile that replaces a shipped one of the same name.
Fails on an invalid `CFP_DATA_DIR`.

|`seed-update`
a|* `--profile <id>`, required
* `--seed-dir <path>`, required
* `--user-seed-dir <path>`: as for `seed-status`
* `--files <list>`: comma-separated seed files to take besides `profile.md`, as `seed-status` prints them
* `--all`: take every changed or missing seed file

`--files` and `--all` exclude each other.
|`profile`, `from_version`, `to_version`, `updated`, `added`, `skipped`, `source`, `warnings`.
Works only on an `outdated` profile, also one that exists only in the personal profiles folder.
An unknown profile fails with `no seed profile '<id>' in <plugin dir> or <user dir>`.
`profile.md` is always replaced.
Replaced profile and event files keep the approval flag of the store copy.
|===

[#proposal]
== proposal

Proposals.
A call that changes the content of a `ready` proposal moves it back to `draft` and adds `reset_to_draft: true` to its result.
This applies to `set-field`, `set-bio-text`, and `set-meta`.

[cols="1,2,2"]
|===
|Subcommand |Options |Returns

|`list`
a|* `--status <status>`
* `--event <id>`
* `--talk <id>`

Each given option filters the list.
|`proposals` (id, talk, title, profile, event, session type, status, and dates), sorted by status, `problems`.

|`show`
a|* `--proposal <id>`, required
|The proposal's front matter keys, `fields` (text per field id), and `bio`.

|`create`
a|* `--talk <id>`, required
* `--profile <id>`, required
* `--event <id>`, required
* `--session-type <id>`, required
* `--angle <text>`
|`path`, `id` (`<event>--<talk>`).
Needs an existing talk, an approved profile and event, a session type of the event, and no proposal with that id yet.

|`set-field`
a|* `--proposal <id>`, required
* `--field <id>`, required
* `--text-file <file>`, required
|`field`, `chars`, `limit`, `limit_status`, `status`.

|`set-meta`
a|* `--proposal <id>`, required
* `--from-json <file>`: a JSON object with any of the keys `track`, `audience_level`, `bio`, `resources`, `co_speakers`, `co_speaker_genders`, `angle`, `session_type`
* `--track <value>`
* `--audience-level <value>`
* `--bio <name>`: a bio variation, copied into the proposal
* `--resources <ids>`: comma-separated resource ids; an empty string clears them
* `--co-speakers <json>`: a JSON list, for example `["Name, Company"]`
* `--co-speaker-genders <json>`: a JSON list of strings
* `--angle <text>`
* `--session-type <id>`

Flags win over the file.
|`updated` (the keys set).

|`set-bio-text`
a|* `--proposal <id>`, required
* `--text-file <file>`, required
|`chars`, `limit`, `limit_status`, `status`, `on_form`.

|`mark-voice-pass`
a|* `--proposal <id>`, required
|`voice_pass: true`.
|===

`status` in the results of `set-field` and `set-bio-text`, and in each entry of `fields` and in `bio` for `count` and `pasteview`, is one of `ok`, `over`, `unverified`, `no-limit`, or `not-on-form` for a bio the form does not have.
xref:internals/rules.adoc#character-counts-and-limit-statuses[How rules and verdicts are computed] explains the counts.

[#preflight]
== preflight

The hard rule check.
In the results of both calls, `ok` means the call succeeded and `passed` is the rule verdict: true when no finding has severity `disqualify`.
Both calls store the result on the proposal.

[cols="1,2,2"]
|===
|Call |Options |Returns

|`preflight`
a|* `--proposal <id>`, required
|`passed`, `findings`, `manual` (rules the code does not compute), `problems`.

|`preflight add-finding`
a|* `--proposal <id>`, required
* `--from-json <file>`: a JSON object with any of the keys `rule`, `severity`, `text`, `source`
* `--rule <id>`
* `--severity <severity>`: `disqualify` or `warn`
* `--text <text>`
* `--source <text>`

Flags win over the file.
`rule` and `text` are required, as flags or in the file.
`severity` is required only for a rule id that is not in the profile; a profile rule brings its own.
|`passed`, `findings` (all stored findings, the new one included).
|===

xref:internals/rules.adoc[How rules and verdicts are computed] describes every rule and the stored pre-flight result.

[#status]
== status

The proposal lifecycle.

[cols="1,2,2"]
|===
|Subcommand |Options |Returns

|`set`
a|* `--proposal <id>`, required
* `--to <status>`, required: `draft`, `ready`, `submitted`, `accepted`, `presented`, `rejected`, or `withdrawn`; an unknown value is a domain error (exit 1)
* `--date <date>`: an ISO date, default today
* `--force`: set `ready` without the ready check
|`from`, `to`, `date`, `side_effects`.
The move must be one of the transitions the lifecycle allows.
`accepted` adds the proposal as a calibration example, and `presented` records an outing on the talk.

|`ready-check`
a|* `--proposal <id>`, required
|`can_ready`, `reasons`.
|===
