`cfp` ships six commands: `/cfp:init`, `/cfp:draft`, `/cfp:bio`, `/cfp:profile`, `/cfp:check`, and `/cfp:status`.
Each command passes its arguments to the `cfp` skill of the same name.
The skill `cfp:committee-review` has no command file.

== Invoke a command or a skill

Type `/` in Claude Code to see the commands available to you, or `/` followed by letters to filter them.
Claude Code recognizes a command only at the start of your message.
The text after the command name becomes its arguments.

Plugin skills are namespaced as `/plugin-name:skill-name`.
So `cfp:committee-review` runs when you type `/cfp:committee-review`.
Claude also uses skills when they are relevant, so a request in your own words, such as "run the committee review", can load the skill.

The argument line under each command below is its argument hint, which Claude Code shows during autocomplete.

[#init]
== /cfp:init

[source,text]
----
/cfp:init [--store <path>]
----

First-use setup and seed profile copy.
On later runs, it handles the update of a shipped profile that a newer plugin version brought.

[cols="1,3"]
|===
|Argument or choice |Effect

|`--store <path>`
|Uses this store path without asking.

|no argument, new store
|Proposes the store that cfp resolves without `--store`, as an absolute path and as the first, recommended choice: `CFP_STORE` when set, else the store in the config file, else `<data folder>/store` (by default `~/.local/share/cc-cfp/store`).
An Obsidian vault is never the default.
When `~/Obsidian/<vault>` folders exist, the `Talks` folders of up to three vaults, sorted by name, are further choices.
"Other" takes a path as free text.
The config folder is `CFP_CONFIG_DIR`, else `$XDG_CONFIG_HOME/cc-cfp`, else `~/.config/cc-cfp`, and setup writes the store path to `config.json` there.
The data folder is `CFP_DATA_DIR`, else `$XDG_DATA_HOME/cc-cfp`, else `~/.local/share/cc-cfp`.
xref:reference/config.adoc#store-resolution[Configuration] lists the resolution order and both folders.

|personal profiles
|Setup also copies each profile folder in `<data folder>/profiles/` that holds a `profile.md` into the store, next to the shipped profiles, and the update check compares the store copy with it.
A personal profile with the name of a shipped one replaces it, and cfp shows a warning once per run.
cfp never creates `<data folder>/profiles/`; create it and add a folder per conference in the format of the shipped profile.
xref:overview/install.adoc#where-cfp-keeps-its-files[Where cfp keeps its files] lists the `seed_version` rules.

|`keep it as it is`
|On an initialized store: no setting changes; goes on to the check of the shipped profiles.

|`re-run setup on it`
|On an initialized store: runs the setup steps again to update the settings and keeps all data.

|`use a different path`
|On an initialized store: asks for a new path, then for the settings.
|===

Explained in xref:overview/install.adoc[Install and first run] and xref:profiles/refresh.adoc[Refresh a profile and update shipped ones].

[#draft]
== /cfp:draft

[source,text]
----
/cfp:draft [--profile <id>] [--event <id>] [--talk <id>] [--proposal <id>] [--from <path or URL>]
----

Interactive drafting from an idea, existing material, a stored talk, or an old proposal.
The flow covers the story interview, title and abstract angles, every form field, the committee review loop, the voice pass, pre-flight, and the paste view.

[cols="1,3"]
|===
|Argument |Effect

|no argument
|When draft proposals exist, asks whether to resume one of them or to start a new one.

|`--profile <id>`
|Skips the profile question, which is also skipped when only one profile exists.

|`--event <id>`
|Skips the event question.

|`--talk <id>`
|Skips the question for the input source.

|`--proposal <id>`
|Resumes this proposal at its first incomplete step.

|`--from <path or URL>`
|Starts from existing material: a local file or a public URL.
Skips the question for the input source.
|===

Explained in xref:user/draft.adoc[Draft a proposal].

[#bio]
== /cfp:bio

[source,text]
----
/cfp:bio [new | list | edit <name> | delete <name> | resource add | resource list | resource delete <id>]
----

Bio variations (third person, with character counts) and speaker resources (recordings, repositories, blog posts, prior sessions).

[cols="1,3"]
|===
|Subaction |Effect

|no argument or `list`
|Lists bios and resources.

|`new`
|Creates a bio variation.

|`edit <name>`
|Edits a bio variation.

|`delete <name>`
|Deletes a bio variation.

|`resource add`
|Adds a speaker resource.

|`resource list`
|Lists resources.

|`resource delete <id>`
|Deletes a resource.
|===

Any other argument shows this list and asks which subaction to run.

Explained in xref:user/bios.adoc[Bios and speaker resources].

[#profile]
== /cfp:profile

[source,text]
----
/cfp:profile [new <name or URL> | refresh <id> [--event <id>] [--screenshots <paths>] | show <id> | list]
----

Researches a conference's public CFP pages and form screenshots into a profile, refreshes an edition's event override, and shows profiles and deadlines.

[cols="1,3"]
|===
|Subaction |Form

|`new`
|`new <conference name or CFP URL> [--event <id or URL>] [--screenshots <path,...>]`

|`refresh`
|`refresh <profile-id> [--event <id or URL>] [--screenshots <path,...>]`

|`show`
|`show <profile-id> [--event <event-id>]`

|`list`
|`list`, also the default without arguments
|===

The skill accepts `--event` and `--screenshots` with `new` as well, and `--event` with `show`, although the argument hint lists them only for `refresh`.
`--screenshots` takes a comma-separated list of image paths.
Images pasted into the conversation count as screenshots too.

Explained in xref:profiles/new.adoc[Research a new conference], xref:profiles/refresh.adoc[Refresh a profile and update shipped ones], and xref:profiles/index.adoc[How profiles work].

[#check]
== /cfp:check

[source,text]
----
/cfp:check <proposal-id>
----

Standalone pre-flight: hard rules, the profile's custom rules, the audience level check, character counts, and whether the proposal can become ready.

Without a proposal id, `cfp` lists your proposals and asks which one to check.
The check works on a proposal in any status.

Explained in xref:user/preflight.adoc[Pre-flight, counts, and the paste view].

[#status]
== /cfp:status

[source,text]
----
/cfp:status [list [--status <s>] | set <proposal-id> <status> [--date <d>] | reopen <proposal-id> [--event <id>]]
----

Tracks the proposal lifecycle.

[cols="1,3"]
|===
|Subaction |Effect

|no argument or `list [--status <s>]`
|Lists proposals grouped by status.

|`set <id> <status> [--date <d>]`
|Changes a proposal's status.

|`reopen <id> [--event <id>]`
|Starts a new draft from a rejected or withdrawn proposal.
|===

Statuses: `draft`, `ready`, `submitted`, `accepted`, `presented`, `rejected`, `withdrawn`.
Any other argument shows this list and asks.

Explained in xref:user/status.adoc[Track a proposal's status].

[#committee-review]
== cfp:committee-review (skill)

[source,text]
----
/cfp:committee-review --proposal <id> [--examples <n>]
----

One simulated program committee round on a stored proposal.
`/cfp:draft` runs it in its review loop.

[cols="1,3"]
|===
|Argument |Effect

|`--proposal <id>`
|Required.
Without it, `cfp` lists your proposals and asks which one.

|`--examples <n>`
|Number of calibration examples in the review packet.
Default 3.
|===

Explained in xref:user/review.adoc[Committee review and voice pass].
