Two things stand between you and your first proposal.
`cfp` has to be installed in Claude Code, and it needs a store, the folder where it keeps your talks, proposals, bios, and conference profiles.
This page takes care of both.
If you haven't met cfp yet, xref:index.adoc[What cfp does] gives you the big picture first.

== What you need

* Claude Code with plugin support.
* Python 3.10 or newer on your `PATH`.

You don't need a virtual environment, because cfp's scripts use only Python's standard library and run with `python3 -I`.

== Install cfp

You install cfp from a local clone of its repository.
In Claude Code's terms, a marketplace is a catalog of plugins, and Claude Code has to know about a marketplace before you can install from it.
The cc-cfp repository is its own marketplace, called `cc-cfp-marketplace`, and one `make` target registers it and installs the plugin.

. Clone the repository and install the plugin:
+
[source,bash,subs="attributes+"]
----
git clone {cfp-repo}.git
cd cc-cfp
make install
----
+
Here's what `make install` does.
It adds your clone to Claude Code as the marketplace `cc-cfp-marketplace`, or updates that marketplace when it's already there.
If cfp is already installed, it removes it first.
Then it runs `claude plugin install cfp@cc-cfp-marketplace`.
Installed from the shell like this, a plugin gets user scope by default, which means it's enabled for you in every project on this machine.
+
Check: Claude Code's plugin list includes cfp.
+
[source,bash]
----
claude plugin list
----
// expect: contains "cfp@cc-cfp-marketplace"

. Start Claude Code with `claude`.
A plugin you install from your shell loads the next time you start Claude Code.
Already have a session open?
Run `/reload-plugins` in it instead.
+
Check: when you type `/` in Claude Code, the list shows cfp's commands in the form `/cfp:<name>`, for example `/cfp:init` and `/cfp:draft`.

=== Optional: cc-prose for the voice pass

`cfp` runs the cc-prose humanizer in a step called the voice pass (xref:index.adoc[What cfp does] explains both).
Without cc-prose, cfp skips the voice pass and tells you so.
If you want it, cc-prose installs the same way as cfp: clone {prose-repo}[its repository] and run `make install` there.

== Set up your store

`cfp` keeps everything it writes in your store, so the store comes next.
`/cfp:init` sets it up and copies the KubeCon + CloudNativeCon profile into it, so you can start drafting right after.
If you run a different `/cfp:` command first, cfp tells you the store isn't set up yet and offers to run `/cfp:init` for you.

. In Claude Code, run:
+
[source,text]
----
/cfp:init
----

. Answer its questions.
It asks them one at a time:
+
* *Where should the store live?*
The default, offered first and shown as a full path, is `~/.local/share/cc-cfp/store`.
More precisely, it's the store that cfp resolves without `--store`: `CFP_STORE` when set, else the path in your config file, else `<data folder>/store` (see <<where-cfp-keeps-its-files>>).
If `~/Obsidian` holds vaults, you also get the `Talks` folder of up to three of them, sorted by name, as further choices.
"Other" lets you type any path, for example the `Talks` folder of another vault.
* *Your name.*
It's required, and cfp uses it in third-person bios and in drafts.
* *Your company or affiliation.*
It's optional.
`cfp` uses it in bios and for any conference rule that compares speaker affiliations.
* *A voice profile.*
If you have named cc-prose voice profiles, cfp offers them, plus "None (humanize only)".
If it finds none, it says so, and the voice pass runs the humanizer without a named voice.
* *Review rounds.*
This is the maximum number of committee review rounds before the review loop stops: 3 by default, anything from 1 to 10.

+
Check: `/cfp:init` ends with a short summary that lists the store path, the config file, your personal profiles folder, the seeded profiles, your name, company, voice profile, and review rounds, and the commands to try next: `/cfp:draft`, `/cfp:bio new`, and `/cfp:profile list`.

== What /cfp:init creates

`/cfp:init` creates the store folder, including any missing parent folders.
In the store folder, it creates:

* the folders `profiles/`, `talks/`, `proposals/`, `bios/`, and `resources/`;
* `config.md`, with your name, company, voice profile, review rounds, and default profile;
* a copy of the shipped KubeCon + CloudNativeCon profile under `profiles/`, marked as approved so drafting works right away, and set as your default profile;
* a copy of each of your personal profiles, also marked as approved.

Outside the store, it writes `config.json` in your config folder (by default `~/.config/cc-cfp/config.json`), which holds the store path.
It doesn't create the data folder or its `profiles/` folder, unless the store itself goes there.

Every file in the store is plain markdown.
You can edit it in any editor or open the store as an Obsidian vault.
xref:internals/store.adoc[Store files] describes what each file holds.

Want to see the result from your shell?
The store CLI ships in the clone, so you can ask it directly.

Check: in your cc-cfp clone, the store CLI prints one line of JSON with your store path and `"exists": true`.

[source,bash]
----
python3 -I cfp/scripts/cfp_store.py config show
----
// expect: matches /"exists": true/

The same line also names the config file it read (`config_file`), the file the next setup writes (`config_write_path`), the data folder (`data_dir`), your personal profiles folder (`user_profiles_dir`), and where the store path came from (`store_source`: `argument`, `environment`, `config`, or `default`).

== Where cfp keeps its files

`cfp` uses two folders outside the store.
Both follow the XDG Base Directory layout, and an environment variable can move each of them.

[cols="1,2,2"]
|===
|Folder |Location, first match wins |Holds

|Config folder
|`CFP_CONFIG_DIR`, then `$XDG_CONFIG_HOME/cc-cfp`, then `~/.config/cc-cfp`
|`config.json` with the store path

|Data folder
|`CFP_DATA_DIR`, then `$XDG_DATA_HOME/cc-cfp`, then `~/.local/share/cc-cfp`
|`profiles/` with your personal profiles, and the default `store/`
|===

`cfp` finds the store in this order: `--store <path>` on a store CLI call, then the `CFP_STORE` environment variable, then the `store` entry in `config.json`, then the default `<data folder>/store`.
The context hook and the store CLI use the same rules, so they always agree on the store.

These rules apply to the variables:

* `XDG_CONFIG_HOME` and `XDG_DATA_HOME` are ignored when they're empty or not absolute.
* `CFP_CONFIG_DIR`, `CFP_DATA_DIR`, and `CFP_STORE` count as unset when they're empty.
A leading `~` is expanded.
A value that is still relative makes every command that needs it fail with an error that names the variable, for example `CFP_STORE must be an absolute path, got 'talks'`.
* When `CFP_CONFIG_DIR` isn't set and the config folder holds no `config.json`, cfp reads `~/.config/cc-cfp/config.json`, the location of earlier versions.
Setup always writes to the config folder.

=== Personal conference profiles

Conference profiles that cfp doesn't ship go into `<data folder>/profiles/<id>/`, in the same format as the shipped profile: a folder with `profile.md` and optional `events/` and `examples/` folders.
A folder without `profile.md` is skipped.
The folder name is the profile id, so it must start with a letter or digit and use only letters, digits, `.`, `_`, and `-`; `/cfp:init` skips other folders with a warning.
A profile whose `profile.md` can't be read is skipped with a warning that names the file, and the next `/cfp:init` run copies it once you've fixed it.
A symlinked profile folder and a symlinked `profile.md` are copied as regular files, and symlinked `events/` or `examples/` folders and symlinked files in them are skipped, so the store never writes back into your own files.
`/cfp:init` copies your profiles into a new store next to the shipped ones, and its update check compares the store copy with your profile.
`cfp` never creates this folder, so create it yourself when you need it.

* `seed_version` in `profile.md` is an ISO date (`YYYY-MM-DD`).
Raise it when you change your profile, and the next `/cfp:init` run offers the update.
* A profile without `seed_version` is copied once, and its store copy is never offered an update.
* A personal profile with the name of a shipped one replaces the shipped one, and cfp warns about it.
To have your variant offered over an existing store copy of the shipped profile, give it a later `seed_version` than the shipped one.

== Running /cfp:init again

Once the store exists, `/cfp:init` shows you its current path and asks what you want:

* `keep it as it is` changes no settings and goes straight to checking the shipped profiles;
* `re-run setup on it` asks the setup questions again to update your answers, and all your data is kept;
* `use a different path` asks for a new path and runs the setup there.

Run `/cfp:init` again after every plugin update, too.
Your store keeps its own copy of the shipped profile.
When the shipped one is newer, `/cfp:init` shows you the differences and offers to update your copy.
xref:profiles/refresh.adoc[Refresh a profile and update shipped ones] walks through that update.

== A second store with CFP_STORE

`CFP_STORE` comes before the config file in the store order (see <<where-cfp-keeps-its-files>>).
It points a session at a second store without rewriting the config file, and cfp's prompt hook honours it too.

. Set up the second store in Claude Code, giving its path right away:
+
[source,text]
----
/cfp:init --store ~/cfp-store-2
----
+
With `--store`, `/cfp:init` takes that path without asking for one.
+
[WARNING]
====
Setting up a store writes its path to `config.json` in your config folder, so the second store is now your default.
The next step makes your first store the default again.
====

. Start Claude Code without `CFP_STORE`, run `/cfp:init`, choose `use a different path`, and enter your first store's path.
`/cfp:init` asks the setup questions again and writes that path back to `config.json`.
+
Check: the `/cfp:init` summary lists your first store as the store path.

. Start a session on the second store from your shell:
+
[source,bash]
----
CFP_STORE=~/cfp-store-2 claude
----
+
Check: `/cfp:init` in that session shows `cfp-store-2` as the current store path.
Choose `keep it as it is` to leave it unchanged.
+
From your shell, in your cc-cfp clone, the store CLI finds the second store through the same variable.
+
Check: the JSON line shows the `cfp-store-2` path and `"exists": true`.
+
[source,bash]
----
CFP_STORE=~/cfp-store-2 python3 -I cfp/scripts/cfp_store.py config show
----
// expect: matches /cfp-store-2/ and matches /"exists": true/

== When cfp's commands do nothing

There are two ways this shows up.

The `/cfp:` commands don't appear when you type `/`::
A plugin you install from your shell loads the next time you start Claude Code or when you run `/reload-plugins` in an open session, so restart Claude Code or run `/reload-plugins`.
If `claude plugin list` in your shell doesn't show `cfp@cc-cfp-marketplace`, run `make install` again in your clone.

A `/cfp:` command says the plugin seems not to be installed correctly, and stops::
Every `/cfp:` prompt normally gets a block of context from cfp's prompt hook: the plugin's location, your store path, whether the store is set up, and today's date.
When that block is missing, the hook didn't fire, and the command stops with this message.
Run `make install` again in your clone.
